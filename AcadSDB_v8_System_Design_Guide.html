01 Overview

The PUPLC Intelligent Class Scheduling System automates and manages academic class schedules using a Case-Based Reasoning (CBR) + Random Forest AI engine for generation and a Constraint Satisfaction Problem (CSP) engine for real-time conflict detection.

The system uses two separate editors with clearly defined purposes:

  • Final Schedule Editor — for building and approving the official schedule that appears in SIS.
  • Local Arrangement Editor — for managing temporary, day-to-day adjustments on top of the approved schedule.

Schedules go through a 3-status lifecycle (Draft → Approved → Locked), with an Adjustment Period window during which an Approved schedule can still be corrected before it becomes fully locked.

Group key = (programcode, yearlevel, acadyear, term)
Every version rule applies within this group scope.

02 The Two Editors

Final Schedule Editor

Builds and approves the official class schedule. The approved result is what gets uploaded to SIS and seen by faculty.

Save as Draft Approve Schedule
Access: always available to Academic Head
Local Arrangement Editor

Manages temporary changes on top of the official schedule (room swaps, cancellations, makeups). Does NOT modify the official schedule.

Save as Draft Save Locally
Access: unlocked after Approved schedule exists · editable until semester ends
Local Arrangement Editor is locked/hidden if no Approved schedule exists yet for that program + year level + semester. You must go through the Final Schedule Editor first.

When Replaced

When a new version is Approved, the old Approved/Locked version automatically moves to Archive. Archived versions can be restored to Draft at any time via the Version History page.

The Adjustment Period is a configurable window (set in Settings) during which an Approved schedule can still be edited and re-approved. Once the window expires, the schedule becomes Locked automatically.

05 Version State Rules

RuleDescription
Rule 1Only 1 Draft may exist per group key at any time. Saving a new draft overwrites the existing Draft — same version number, updated content.
Rule 2Only 1 Approved version may exist per group key. Approving a Draft archives the current Approved/Locked version (if any) before setting the Draft to Approved.
Rule 3An Approved version is editable only within the Adjustment Period. After the period expires, it automatically becomes Locked.
Rule 4A Locked version is fully immutable. To revise it, use Restore in Version History → it creates a new Draft copy.
Rule 5Restore archives any existing Draft first, then creates a new Draft from the selected Archive. The archived version is preserved.
Rule 6version_number increments each time a new Draft is committed or a version is restored from Archive.
Rule 7Local Arrangement entries are independent of version status. They are overlaid on top of the active Approved/Locked schedule and do not modify schedule_sessions.

06 Adjustment Period Setting

The Adjustment Period applies to the Final Schedule only. It has no effect on Local Arrangements — those remain editable until the semester ends.
Settings → Schedule → Adjustment Period

Configurable number of days after Approval during which the Final Schedule can still be edited. After this window, the schedule automatically becomes Locked.

ScenarioBehavior
Adjustment Period = 7 days, today is Day 3Approved schedule is still editable in Final Schedule Editor
Adjustment Period = 7 days, today is Day 8Schedule automatically becomes Locked — no edits allowed
Adjustment Period = 0Schedule locks immediately upon Approval
Even during the Adjustment Period, "Save as Draft" is still available. Use it for bigger revisions — it saves a Draft copy while the current Approved schedule stays live.

How Locking Works

The system checks approved_at + adjustment_period_days < NOW() on every load. No scheduled job needed — it is evaluated at runtime. The status column is updated to 'Locked' lazily on first access after expiry, or by a nightly cleanup job.

07 Lifecycle Scenarios

Scenario 1 — First-Time Schedule Generation
  1. Academic Head generates schedule via AI engine.
  2. System creates schedule record + schedule_version (status=Draft, v1).
  3. Sessions saved to schedule_sessions.
  4. Local Arrangement Editor is not yet accessible (no Approved version exists).
State: 1 Draft (v1) | Local Arrangement: locked
Scenario 2 — Edit Draft in Final Schedule Editor
  1. Academic Head opens Draft in Final Schedule Editor.
  2. Makes changes to session slots.
  3. Clicks Save as Draft — sessions updated in-place, version number unchanged.
State: 1 Draft (v1, updated) | Local Arrangement: locked
Scenario 3 — Approve the Schedule
  1. Academic Head clicks Approve Schedule.
  2. System checks: existing Approved/Locked version for this group?
    • Yes → Archive the existing Approved/Locked version.
    • No → Skip.
  3. Draft → Approved. Adjustment Period timer starts.
  4. Schedule appears in SIS. Faculty can see it.
  5. Local Arrangement Editor is now unlocked for this group.
State: 1 Approved (v1) | Local Arrangement: unlocked
Scenario 4 — Quick Fix During Adjustment Period
  1. Academic Head spots an error in the Approved schedule (within Adjustment Period).
  2. Opens it in Final Schedule Editor, makes the fix.
  3. Clicks Approve Schedule — Approved version is updated in-place. Old Approved moves to Archive.
State: 1 Approved (v1, corrected), 1 Archive (v1 original)
Scenario 5 — Bigger Revision (Save as Draft First)
  1. Academic Head needs to restructure the schedule significantly.
  2. Opens Final Schedule Editor, makes changes, clicks Save as Draft.
  3. Draft v2 is saved. Current Approved v1 stays live for faculty.
  4. Reviews Draft v2, makes more edits.
  5. Clicks Approve Schedule — Draft v2 → Approved. v1 → Archive.
State: 1 Approved (v2), 1 Archive (v1)
Scenario 6 — Adjustment Period Expires
  1. Adjustment Period ends (e.g., 7 days after approval).
  2. System automatically marks Approved → Locked.
  3. Final Schedule Editor shows read-only view for this version.
  4. To make changes: use Restore in Version History to create a new Draft.
State: 1 Locked (v2), 1 Archive (v1)
Scenario 7 — Local Arrangement (Temporary Change)
  1. Approved/Locked schedule exists. Local Arrangement Editor is accessible.
  2. Academic Head opens Local Arrangement Editor.
  3. Enters a temporary change (e.g., room swap on a specific date).
  4. Clicks Save as Draft → saved as Pending (not yet active).
  5. Reviews and confirms → clicks Save Locally → status becomes Active.
  6. Active local arrangement overlays on the official schedule for that date.
State: Official schedule unchanged | Local arrangement: Active
Scenario 8 — Restore from Archive
  1. Academic Head goes to Version History, selects an archived version, clicks Restore.
  2. System archives any existing Draft.
  3. Creates a new Draft copy from the archived version (new version_number).
  4. Academic Head edits in Final Schedule Editor → Approve when ready.
State: New Draft created | Original Archive preserved
Scenario 9 — Multiple Programs, Same Semester

Each (programcode, yearlevel, acadyear, term) group is fully independent. BSIT Year 1 and BSCS Year 1 in the same semester each have their own Draft/Approved/Locked lifecycle and their own Local Arrangement entries.

08 Auto-Generation Engine

Algorithm: CBR + Random Forest

ComponentRole
Case-Based Reasoning (CBR)Retrieves the most similar past schedule (by program, year level, semester, enrollment) from historical data and uses it as the base template.
Random ForestPredicts optimal time slot assignments based on: room capacity, faculty load, subject type, historical conflict rate, day/time distribution.
CSP Post-ProcessingAfter generation, verifies no Hard Constraint is violated. Violations are logged to schedule_exception_log.

Generation Flow

Input: (program, year level, acad year, term, subjects, faculty, rooms)
  │
  ▼
CBR Retrieval — find closest past schedule
  │
  ▼
Random Forest Prediction — assign time slots, rooms, faculty
  │
  ▼
CSP Verification — check all Hard Constraints
  │
  ├── HC Violations found → log to schedule_exception_log, flag for review
  │
  └── No violations → save as Draft (opens in Final Schedule Editor)

Hard Constraint (HC) Types

HCDescription
HC-1No faculty double-booking (same faculty, same timeslot)
HC-2No room double-booking (same room, same timeslot)
HC-3No student group double-booking (same program/year, same timeslot)
HC-4Subject unit hours must be satisfied within the week
HC-5NSTP subjects: Sunday-only assignment
HC-6Room capacity ≥ expected class enrollment

17 Appendix: Key Design Decisions

DecisionRationale
2 separate editorsFinal Schedule and Local Arrangement serve completely different purposes. One editor merging both caused confusion. Separation makes intent clear for the user and the codebase.
Removed Published statusPublished added an intermediate step that didn't serve a clear purpose when the Academic Head is the sole approver. Draft → Approved is simpler and direct.
Adjustment Period in SettingsMirrors real academic practice — there's always a correction window after releasing a schedule. Making it configurable lets the institution decide their own policy.
Approved → Locked (not immutable from day 1)Small corrections after approval are inevitable. A hard lock from day 1 would force a full restore-edit-approve cycle for a one-field fix. The adjustment period balances flexibility with finality.
Local Arrangement gated behind ApprovedYou cannot adjust something that doesn't officially exist. Prevents orphaned adjustments referencing no official baseline.
Local Arrangement has Pending/Active/ExpiredPending = drafting a change before it goes live. Active = confirmed and in effect. Expired = auto-set at semester end. Independent of Adjustment Period — Local Arrangements remain editable until the semester ends regardless of whether the Final Schedule is Locked.
Archive is restorableSafety net for reverting bad approvals without losing history.
CSP on every Final Schedule Editor saveImmediate feedback prevents approving schedules with HC violations.
